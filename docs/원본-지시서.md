## 1. 기술 스택과 작업 규칙

### 스택
- **언어**: Luau, 모든 파일 상단에 `--!strict`
- **파일 동기화**: Rojo (파일시스템 ↔ Roblox Studio). Claude Code는 Studio를 직접 조작할 수 없으니 **모든 코드는 파일로 작성하고 Rojo로 동기화**하는 구조를 전제로 해.
- **패키지 관리**: Wally
- **데이터 저장**: ProfileStore (세션 락 지원). 설치 방법이 불확실하면 추측하지 말고 개발자에게 확인 요청.
- **린트/포맷**: Selene, StyLua
- **테스트**: 순수 로직(확률, 경제, 배틀 계산)은 Lune으로 Studio 밖에서 실행 가능한 테스트 작성
- **툴 버전 고정**: Aftman 또는 Rokit으로 rojo/wally/selene/stylua/lune 버전 고정

### 작업 규칙 (중요)
1. **Phase 단위로 작업하고, 각 Phase가 끝나면 멈춰서** 변경 요약, 테스트 방법, 남은 이슈를 보고해. 다음 Phase는 승인 후 진행.
2. **로블록스 API를 지어내지 마.** 확신이 없는 API·서비스·정책은 "확인 필요"로 표시하고 공식 문서(create.roblox.com/docs) 확인을 요청해.
3. **서버 권위(server-authoritative)**: 확률 계산, 골드 증감, 레벨 변경, 배틀 결과는 전부 서버에서만. 클라이언트는 요청과 표시만 담당.
4. 게임 밸런스 수치는 코드에 하드코딩하지 말고 **`shared/Config` 모듈에 데이터로** 둬.
5. 모든 서버 함수는 입력 타입 검증부터. 실패는 에러 대신 `{ ok = false, reason = "..." }` 형태로 반환.
6. 커밋 단위는 기능 하나. 커밋 메시지는 한국어로 간결하게.

## 3. 데이터 모델 (ProfileStore)

```lua
export type PlayerData = {
	schemaVersion: number,        -- 마이그레이션용, 현재 1
	gold: number,
	shards: number,               -- 파괴 시 얻는 보조 재화
	weapon: {
		id: string,               -- Weapons 설정의 키
		level: number,            -- 0 ~ MAX_LEVEL
		customName: string?,      -- 필터링 통과한 이름만 저장
	},
	protectTickets: number,       -- 파괴 방지권
	stats: {
		enhanceTries: number,
		enhanceSuccess: number,
		destroyed: number,
		highestLevel: number,
		battleWins: number,
		battleLosses: number,
		rating: number,           -- 배틀 레이팅, 시작 1000
	},
	codex: { [string]: boolean }, -- 도감: "weaponId:level" 달성 여부
	achievements: { [string]: boolean },
	daily: {
		lastLoginDay: number,     -- UTC 기준 일자 (os.time() // 86400)
		streak: number,
		battlesToday: number,
		opponentsToday: { [string]: number }, -- userId → 오늘 대전 횟수
	},
	purchaseHistory: { [string]: boolean }, -- ProcessReceipt 중복 방지 (PurchaseId)
	settings: { sfx: boolean, language: string },
	bannedUntil: number?,
}
```

- 스키마 변경 시 `schemaVersion`을 올리고 `DataService`에 마이그레이션 함수를 추가해. 기존 데이터를 절대 날리지 마.
- `purchaseHistory`는 무한히 커지지 않게 최근 N개(예: 200)만 유지.
- 로드 실패 시 플레이어를 **Kick**하고 재접속 안내. 기본값으로 덮어쓰고 진행하는 건 금지.
- `game:BindToClose`에서 모든 프로필 저장 완료까지 대기.
- Studio에서는 별도 테스트용 스토어 이름 사용 (`[게임명]_DEV`), 라이브는 `[게임명]_PROD`.

## 4. 강화 시스템

### 규칙
- 강화 1회 = 해당 레벨의 비용(골드) 차감 → 서버 난수로 결과 결정.
- 결과 3종: **성공**(+1), **유지**(변화 없음), **파괴**(레벨 0으로 초기화 + 파편 지급).
- 파괴 방지권 사용 옵션: 켜 두면 파괴 결과가 유지로 바뀌고 방지권 1개 소모. 방지권은 **파괴 확률이 0보다 큰 구간에서만** 소모.
- 최대 레벨: `MAX_LEVEL = 20`. 도달 시 강화 버튼 비활성화 + 특수 연출.
- 난수는 `Random.new()`를 서버에서 한 번 생성해 재사용. 클라이언트 난수 절대 사용 금지.

### 확률표 (`Config/EnhanceTable.luau` 초기값, 퍼센트)

|---|---|---|---|---|---|
| 0 | 100 | 0 | 0 | 10 | 0 |
| 1 | 95 | 5 | 0 | 20 | 5 |
| 2 | 90 | 10 | 0 | 40 | 15 |
| 3 | 85 | 15 | 0 | 70 | 30 |
| 4 | 80 | 20 | 0 | 110 | 55 |
| 5 | 70 | 30 | 0 | 160 | 90 |
| 6 | 65 | 35 | 0 | 230 | 140 |
| 7 | 60 | 40 | 0 | 320 | 210 |
| 8 | 55 | 45 | 0 | 440 | 300 |
| 9 | 50 | 50 | 0 | 600 | 430 |
| 10 | 45 | 50 | 5 | 800 | 620 |
| 11 | 40 | 52 | 8 | 1,050 | 880 |
| 12 | 35 | 55 | 10 | 1,350 | 1,250 |
| 13 | 30 | 58 | 12 | 1,700 | 1,750 |
| 14 | 25 | 60 | 15 | 2,100 | 2,500 |
| 15 | 20 | 62 | 18 | 2,600 | 3,500 |

| 20 | — | — | — | — | 25,000 |

- 각 행의 성공+유지+파괴 = 100 이어야 해. **Lune 테스트로 검증**하고, 서버 시작 시에도 assert.
- 파괴 시 파편 지급량: `floor(현재레벨^1.5)`. 파편 50개 = 파괴 방지권 1개로 교환 가능.
- 판매: 현재 무기를 판매가에 팔고 레벨 0 새 무기로 교체.

### 확률 버프 이벤트
- `LiveOpsService`가 이벤트 설정을 DataStore(또는 MemoryStore)에서 주기적으로 읽어옴.
- 버프 적용 방식: 성공 확률에 `+x%p`, 그만큼 **유지 확률에서 차감** (파괴 확률은 건드리지 않음). 유지가 0 미만이 되면 성공 상한을 조정.
- 적용 중인 이벤트와 **최종 확률을 UI에 항상 표시**.

### 요청 처리 흐름 (EnhanceService)
1. RateLimiter 통과 확인 (플레이어당 초당 최대 3회, 동시 처리 1건: 처리 중이면 거절)
2. 프로필 로드 상태 확인
3. 레벨 < MAX, 골드 ≥ 비용 확인
4. 골드 차감 → 결과 계산 → 레벨/통계/도감 갱신을 **한 함수 안에서 yield 없이** 처리 (중간 yield 금지로 레이스 컨디션 방지)
5. 결과 반환: `{ ok, result = "success"|"keep"|"destroy"|"protected", newLevel, gold, shardsGained }`
6. `AnalyticsService` 경제 이벤트 로그 (골드 싱크)

## 5. 배틀 시스템

### 흐름
1. 플레이어 A가 같은 서버의 플레이어 B에게 도전 신청 (또는 "아무나 매칭")
2. B가 15초 내 수락/거절. 무응답 = 거절
3. 서버가 승패 계산 → 결과 연출 → 보상 지급
4. **배틀로 무기가 파괴되거나 레벨이 떨어지지 않음.** 걸리는 건 골드 보상과 레이팅뿐.

### 승률 공식 (`Pure/BattleLogic.luau`)
- `P(A 승) = 1 / (1 + 10^((LvB - LvA) / K))`, `K = 4`
- 같은 레벨이면 50%, 4레벨 차이면 약 91% (상위 쪽)
- 보상: 승자 `BASE_REWARD(=30) * (1 + 0.1 * LvB) * 역전 배율`. 역전 배율 = 이길 확률이 낮았을수록 큼 (`1 / P(승)`을 최대 3으로 캡)
- 패자: 참가 보상 5골드
- 레이팅: Elo 방식, K-factor 24

### 어뷰징 방지
- 하루 배틀 보상 횟수 상한 `DAILY_BATTLE_REWARD_CAP = 30`, 초과 시 배틀은 가능하되 보상 없음
- 같은 상대와는 하루 보상 최대 3회
- 배틀 쿨다운 10초
- 부계정 파밍 방지: 계정 생성 3일 미만(`Player.AccountAge < 3`)은 배틀 보상 50%

## 6. 경제 설계

- 골드 획득처: 출석(연속 출석 보너스), 배틀, 무기 판매, 도감/업적 보상, 플레이 시간 보상(15분마다 소량)
- 골드 소비처: 강화, 무기 외형 변경, 방지권 구매
- **`tools/simulate_economy.luau` 작성**: 확률표와 경제 설정을 읽어 가상 플레이어 10만 명을 시뮬레이션하고 다음을 출력해.
  - 레벨 k 최초 도달까지 **기대 골드와 분포(중앙값, 90퍼센타일)**
  - 파괴 횟수 분포
  - 일일 획득 골드 기준 레벨 10/15/20 도달 예상 일수
- 시뮬 결과를 보고 "레벨 20은 헤비 유저 기준 [N]주" 같은 목표에 맞춰 수치 조정 제안을 해 줘. **수치 변경은 제안만 하고 적용은 승인 후.**

## 7. 수익화 (로블록스 정책 준수)

- **게임패스**: 골드 획득 +20%, 무기 외형 슬롯 확장, VIP 채팅 태그 등 편의/꾸미기 위주
- **개발자 상품**: 골드 팩, 파괴 방지권 묶음
- **금지/주의**
  - Robux로 **확률형 결과를 직접 구매하는 상품**(예: "유료 강화권으로 확률 뽑기")을 만들면 로블록스의 유료 랜덤 아이템 규정 적용 대상이야. 이 경우 **구매 전 확률 공개가 필수**이고, 한국 이용자 대상이면 국내 확률형 아이템 표시 규정도 고려해야 해. 기본 설계는 **확률 결과 자체를 Robux로 팔지 않는 방향**으로 가고, 필요하면 개발자에게 먼저 확인받아.
  - 확률표는 상품 여부와 관계없이 **강화 화면에서 항상 열람 가능**하게.
- **ProcessReceipt 구현 요구사항**
  - 프로필 미로드 시 `NotProcessedYet` 반환
  - `purchaseHistory[PurchaseId]`로 중복 지급 방지
  - 지급과 기록을 같은 프로필 업데이트 안에서 처리
  - 콜백은 서버 전체에 **딱 한 번만** 설정
- 상품 ID는 전부 `Config/Products.luau`에서 관리 (값은 개발자가 채움: `[게임패스 ID]`, `[상품 ID]`)

## 8. UI/UX

- **컨셉**: 화면 중앙에 무기, 하단에 큰 강화 버튼, 우측(모바일은 상단 접이식)에 "결과 피드" — 채팅 로그처럼 최근 결과가 한 줄씩 쌓이는 구조로 봇 게임 감성 재현
- 결과 피드 예시 문구 톤: 짧고 리듬감 있게, 오리지널 캐릭터 "[NPC 이름]"의 대사로 출력
- 텍스트 명령어도 지원: `TextChatService`의 `TextChatCommand`로 `/강화`, `/판매`, `/배틀 [닉네임]`, `/정보` 등록. 버튼과 명령어는 같은 서버 경로를 탄다.
- 서버 전체 알림: 누군가 15강 이상 성공하면 서버 채팅에 시스템 메시지
- 연출: 성공(빛·상승음), 유지(짧은 흔들림), 파괴(깨짐 파티클 + 화면 흔들림). **서버 응답을 받은 뒤에만** 결과 연출 시작
- 강화 버튼 중복 입력 방지: 요청 중에는 버튼 비활성화
- 모든 UI는 `UIScale`/`UIAspectRatioConstraint` 기반 반응형, 최소 터치 영역 44px 상당
- 무기 이름 짓기: `TextService:FilterStringAsync`로 필터링 후 저장, 표시할 때도 필터링 결과 사용
- 다국어: `LocalizationTable`로 한국어/영어 문자열 관리. 코드에 한국어 문자열 직접 박지 마.

---

## 9. 도감 · 업적 · 랭킹

- 도감: 무기 종류 × 레벨 구간(5/10/15/20) 달성 기록, 칸마다 소량 골드 보상
- 업적 예시: 첫 파괴, 10연속 유지, 방지권 없이 15강, 배틀 100승 등 15개 이상
- 랭킹: `OrderedDataStore`로 "최고 강화 레벨", "배틀 레이팅" 전체 순위. 쓰기는 플레이어 퇴장 시 + 5분 주기로 제한 (예산 초과 방지). 로비에 상위 50명 보드

## 10. 보안 · 안정성 체크리스트

- [ ] 모든 RemoteEvent/RemoteFunction 인자 타입·범위 검증
- [ ] 클라이언트가 보낸 레벨/골드/결과 값은 절대 신뢰하지 않음
- [ ] 플레이어별 레이트 리밋 + 동시 요청 락
- [ ] DataStore 호출은 재시도(지수 백오프) + 예산 확인(`DataStoreService:GetRequestBudgetForRequestType`)
- [ ] 서버 종료 시 저장 보장
- [ ] 관리자 명령은 `Config`의 관리자 UserId 목록만 허용, 모든 관리자 행동 로그
- [ ] 이상 탐지: 짧은 시간에 골드 급증 시 로그 + 관리자 알림용 기록
- [ ] 차단(`bannedUntil`) 체크를 로드 시점에 수행

## 11. 라이브 운영 기능 (LiveOpsService / AdminService)

- 원격 설정: 확률 버프 이벤트(시작/종료 시각 UTC, 버프량), 공지 문구, 점검 모드 플래그
- 점검 모드: 신규 강화/배틀 요청 차단 + 안내 메시지
- 관리자 명령: 골드 지급/회수, 레벨 설정, 차단/해제, 이벤트 on/off, 특정 유저 데이터 조회
- 로그: `AnalyticsService`의 경제 이벤트(골드 source/sink)와 퍼널 이벤트(튜토리얼 단계) 기록 — 정확한 API 시그니처는 문서 확인 후 사용
